# NextRS v0.1.0-rc.2

**Prerelease.** The second release candidate of NextRS v0.1.0. It is
experimental software.

NextRS serves the output of an official Next.js `next build` from a single
Rust binary with embedded V8. It replaces `next start`, not `next build`.

## Overview

rc.2 is a compatibility, correctness and efficiency update to
v0.1.0-rc.1. It closes the two gaps that kept real applications from
running on rc.1 as they run on `next start`:

- builds with a Next.js **deployment ID** were refused at startup;
- responses were never **compressed**.

It also adds HTTP byte ranges, caches the gzip copies of responses that
cannot change, and makes RSC requests to route handlers behave as they do
on `next start`.

Installation, configuration and operation: `README.md` in the archive, and
`release/README.md` in the repository.

## Scope

| | |
|---|---|
| Platform | Linux x86_64, glibc 2.35 or later (unchanged) |
| Next.js | 16.4.6 (primary) and 16.4.5, React 19.3.1 |
| Other Next.js 16.x | Starts with a warning (untested) |
| Other Next.js majors | Refused at startup |
| JavaScript engine | Embedded V8; isolates configurable (`--isolates`) |

## What's new

### 1. Deployment ID compatibility

Builds with `deploymentId` in `next.config` (or `NEXT_DEPLOYMENT_ID` at
build time) now start and are served as `next start` serves them:

- the routes-manifest `onMatchHeaders` rules that Next.js 16.4.6 writes are
  applied as `next start` applies them, so RSC and `/_next/data` responses
  carry `x-nextjs-deployment-id`;
- the JavaScript runtime gets `NEXT_DEPLOYMENT_ID` as `next start` sets it;
- client navigation stays client-side within a deployment, and a response
  from another deployment makes the client load the page in full (the
  version-skew signal), as with `next start`;
- a malformed or unknown `onMatchHeaders` entry is refused at startup
  rather than ignored.

rc.1 refused these builds at startup.

### 2. Gzip HTTP compression

Responses are compressed as `next start`'s compression middleware
compresses them, with the same switch: `compress` in `next.config`
(default `true`).

- gzip, for compressible types (HTML, RSC payloads, JSON, JavaScript, CSS,
  SVG and other text) from 1 KiB, and for streamed responses;
- streaming is preserved: each chunk is compressed and flushed before the
  next, so streamed HTML, RSC and partial prerendering arrive as
  progressively as without compression;
- `Vary: Accept-Encoding` on every compressible response;
- never compressed: HEAD, `204`/`304`, partial responses, images,
  already-encoded bodies and `Cache-Control: no-transform`.

### 3. A bounded cache of compressed immutable responses

A response whose bytes cannot change while the server runs is compressed
once, and the compressed copy is reused:

- files under `/_next/static`, keyed by path and file identity (a file
  replaced on disk is compressed again);
- prerendered App Router pages (HTML, RSC payloads, segment prefetches)
  served from the build.

Nothing dynamic or personalized is cached: SSR, route handlers, Server
Actions, streamed RSC, ISR, partial prerendering, Draft Mode, `public/`
files and image optimizer output are compressed per request.

- `--compression-cache MIB` bounds the memory, **32 MiB by default**;
  least recently used copies are dropped beyond it, and bodies over 4 MiB
  are not cached;
- `--compression-cache 0` turns the cache off;
- concurrent first requests for one response compress it once;
- hits, misses, evictions and bytes held are on the metrics endpoint
  (`nextrs_compression_cache_*`).

### 4. HTTP byte ranges

Files under `/_next/static` and `public/` answer a single byte range with
`206 Partial Content` and advertise `Accept-Ranges: bytes`, as on
`next start`. Only the requested bytes are read from disk.
`If-None-Match` and `If-Modified-Since` are evaluated first, so a
revalidation is a `304` whatever the range.

### 5. RSC route-handler parity

An RSC request (`rsc: 1`) to an App Router route handler is now validated
as `next start` validates it, including its redirect. A repeated `rsc`
header is no longer treated as an RSC request, and
`experimental.validateRSCRequestHeaders: false` is honoured.

## Performance

Measured on the local benchmark fixture, on one x86_64 machine, with a warm
cache. These numbers compare the final rc.2 code with the earlier rc.2
implementation, which compressed every response on every request. They are
not cloud measurements and are not a performance guarantee.

| Workload (gzip clients) | Earlier rc.2 | rc.2 | |
|---|---:|---:|---:|
| Prerendered HTML page | ~22.0k req/s | ~133.2k req/s | 6.1× |
| 229 KB static JavaScript chunk | ~984 req/s | ~24.8k req/s | 25× |
| Every static JS/CSS file, round-robin | ~7.4k req/s | ~53.5k req/s | 7.3× |

- Compression CPU per repeated immutable response fell 8.4× (prerendered
  page) to 33× (the chunk).
- The first gzip request for a response costs what it did before; after
  that, one miss per distinct response per process.
- Responses to clients that do not accept gzip, and dynamic responses (SSR,
  RSC, JSON, streaming), are unchanged within run-to-run spread.
- A cache much smaller than the set of hot assets gets no hits and is about
  9 % slower than no cache. The default 32 MiB held Velasia Airways' whole
  static set (465 KB compressed) about 70 times over.

## Compatibility and correctness

Tested against `next start` on Next.js 16.4.6 (and 16.4.5) on Linux:

- the HTTP compatibility suites, including a deployment-ID build of the
  fixtures and a browser deployment-ID test;
- 480 RSC requests to route handlers, each equal to `next start`'s answer;
- byte ranges, conditional requests and compression, checked response by
  response;
- streaming and partial prerendering, Cache Components, Server Actions.

NextRS does not claim compatibility with every Next.js application. The
public matrix is `engineering/compatibility.md`.

### Intended differences from `next start`

| Behaviour | `next start` | NextRS rc.2 |
|---|---|---|
| ETag of a compressed response | Strong ETag kept | Weak (`W/"…"`); `If-None-Match` still revalidates with `304` |
| `Accept-Ranges` on a compressed response | Kept | Removed |
| Encodings | gzip and deflate | gzip only; a client that accepts only deflate gets the response uncompressed |
| Cached gzip response | Streamed chunked | Sent with `Content-Length` |
| Partial (`206`) response to a gzip client | Partial body gzipped under an identity `Content-Range` | Always the uncompressed bytes (identity), so `Content-Range` describes what is sent |
| Unsatisfiable range (`bytes=<size>-`, `bytes=-0`) | `500` | `416` with `Content-Range: bytes */<size>` (RFC 9110) |
| Malformed range (`bytes=abc`, `bytes=5-2`) | `500` | Ignored: the full `200` |
| Suffix range longer than the file | `500` | `206` for the whole file |
| `HEAD` with `Range` | `206` headers | Ignores `Range`, describes the full response |
| `If-Range` | Weak comparison; any later date matches | Strong comparison: a static file's weak ETag never matches, and a date matches only the exact `Last-Modified`. With gzip negotiated, treated as not matching |
| Deployment ID source | `next.config` evaluated again at start | The build's `deploymentId`; start both servers with the build's ID |

### Remaining limitations

- `multipart/byteranges` is not implemented: several ranges get the full
  `200`, as with `next start`.
- `If-Match` and `If-Unmodified-Since` are not evaluated for static files
  (`next start` answers `500` when they fail).
- `public/` files are compressed per request and never cached, because they
  can change while the server runs.
- On a cache miss the whole body is compressed before it is sent: about
  4 ms of time to first byte for a 229 KB chunk, once per response per
  process.
- Server-side skew routing between deployments is not provided (nor is it
  by `next start`).

The rc.1 limitations are unchanged otherwise: Node.js APIs are a subset
(no network modules, `child_process`, native addons or `zlib` streams),
Web Crypto is partial, JavaScript state is per isolate and caches per
instance, mutations are dispatched at most once, forwarded headers are
permissive by default, and there is no access log or request ID. The full
list is in `README.md`, section 18.

## Installation

**npm** (the package is published under the dist-tag `next`, so install
it by its exact version):

```bash
npm install -D @nextrs/cli@0.1.0-rc.2      # or: pnpm add -D @nextrs/cli@0.1.0-rc.2
npx next build                              # Node.js builds the application
npx nextrs inspect .
./node_modules/@nextrs/cli/bin/nextrs start . --js-runtime embedded-v8
```

**GitHub release binary:**

```bash
V=0.1.0-rc.2
curl -LO https://github.com/nextrs-sh/nextrs/releases/download/v$V/nextrs-v$V-linux-x86_64.tar.gz
curl -LO https://github.com/nextrs-sh/nextrs/releases/download/v$V/nextrs-v$V-linux-x86_64.tar.gz.sha256
sha256sum -c nextrs-v$V-linux-x86_64.tar.gz.sha256
tar -xzf nextrs-v$V-linux-x86_64.tar.gz
sudo install -m 0755 nextrs-v$V-linux-x86_64/nextrs /usr/local/bin/nextrs
nextrs --version        # nextrs 0.1.0-rc.2
```

- **Node.js is still required to build** the application (`next build`).
- **Running needs no Node.js, Rust or Cargo:** the binary loads only the C
  library and `libgcc_s`, and the npm package has no install scripts and no
  dependencies. Its `native/nextrs` is this archive's binary, byte for
  byte.
- **In production,** start the binary directly (`node_modules/@nextrs/cli/bin/nextrs`
  execs it), not through `npx` or `npm start`, so that SIGTERM reaches the
  server.

NextRS is not on crates.io; the crate named `nextrs` there is an unrelated
project.

## Upgrading from rc.1

- No configuration change is needed. Compression is on, as on
  `next start`; set `compress: false` in `next.config` and rebuild to turn
  it off, for example behind a CDN that compresses.
- Remove any workaround that built without `deploymentId` for NextRS.
- Size `--compression-cache` to hold the compressed static set if it is
  larger than 32 MiB, or set it to `0` to turn the cache off.

## Release status

**Experimental.** rc.2 is tested on one x86_64 machine, in CI, and with one
real application (Velasia Airways). It has not run in production, and no
cloud deployment or cloud benchmark has been done with it; those are
separate, later milestones.
