# NextRS v0.1.0-rc.1

**Prerelease.** This is the first release candidate of NextRS v0.1.0, the
project's first release. It is experimental software.

NextRS serves the output of an official Next.js `next build` from a single
Rust binary with embedded V8. It replaces `next start`, not `next build`.

```bash
npx next build
nextrs start . --js-runtime embedded-v8
```

Installation, configuration and operation: `README.md` in the archive, and
`release/README.md` in the repository.

## Scope

| | |
|---|---|
| Platform | Linux x86_64, glibc 2.35 or later |
| Next.js | 16.4.6 (primary) and 16.4.5, React 19.3.1 |
| Other Next.js 16.x | Starts with a warning (untested) |
| Other Next.js majors | Refused at startup |
| JavaScript engine | Embedded V8; isolates configurable (`--isolates`) |

The release compatibility contract classifies every capability as
supported, partial, experimental, unsupported or not tested. It is in
`docs/research/release-compatibility-matrix.md` of the source tree, and its
public summary is `engineering/compatibility.md`.

## Highlights

- **App Router:** server rendering with RSC streaming, Server Actions, ISR
  and on-demand revalidation, Cache Components and partial prerendering.
- **Pages Router:** `getServerSideProps`, `getStaticProps` with ISR, API
  routes, i18n, Preview Mode.
- **`proxy.ts` and middleware** (Node.js runtime), rewrites, redirects and
  headers.
- **`next/image` optimization in Rust,** with no `sharp`, and memory
  admission.
- **Shared data and response cache** across isolates, optionally persisted
  with `--cache-dir`.
- **Outbound `fetch` behind an explicit allowlist,** with SSRF protection.
- **Operations:**
  - health and readiness probes;
  - Prometheus metrics;
  - JSON logs;
  - graceful shutdown;
  - bounded admission with `503` instead of unbounded queues.

> **Pending re-validation.** The results below were measured on an

> build was withdrawn before publication: it read part of its JavaScript
> (deno_web and deno_webidl) from the build machine's Cargo registry at
> run time, so it failed on every other machine. The release workflow's
> clean-install jobs found this. This build compiles the same JavaScript,
> byte for byte, into the binary. The gates below must be re-run on it
> before publication, and this section updated with its checksum.

All of the following ran on the withdrawn build:

- **Six-hour soak at 4 isolates.** Velasia Airways (a full Next.js 16
  application) and a mixed App/Pages Router workload ran side by side, with
  API fault storms, injected JavaScript stalls and client cancellations.
  - 18.8 million requests: 0 unexpected responses, 0 identity leaks,
    0 wrong content, 0 duplicate mutations.
  - Memory levelled off in the last two hours and was returned at idle.
- **Velasia Airways' own Playwright suites,** at 1 and 4 isolates: 101 of
  111 tests pass at each, and the other 10 are mobile variants skipped by
  design. The cross-customer isolation spec also passes.
  - One earlier 1-isolate run failed a metrics test. That failure is
    caused by an application defect when a random booking reference has no
    digit, not by NextRS.
- **The compatibility suites against `next start`,** pinned Next.js
  16.4.6 at 1 and 4 isolates and 16.4.5, plus four independent
  applications.
- **A clean-install smoke test** with an empty environment: no Rust or
  Node.js, and a read-only application directory.
- **`cargo audit`:** no known vulnerabilities.

The gate record is in the Phase 3D release report, a local engineering
record.

## Known limitations

1. **Node.js APIs are a subset.**
   - Node's network modules (`http`, `net`, `dns`), `child_process`,
     `worker_threads`, `vm`, native addons and `zlib` streams are
     unavailable.
   - Database drivers that need TCP sockets do not work.
2. **Web Crypto is partial.** These throw an explicit error: `deriveKey`,
   key wrapping, ECDH, RSA-OAEP, AES-KW, P-521, and RSA key generation.
3. **Timers fire about 1 ms later than Node's,** because of Tokio's timer
   granularity.
4. **JavaScript module state is per isolate.** Caches are per instance and
   are not shared across processes.
5. **Mutations are dispatched at most once.**
   - A Server Action whose isolate fails gives a `502`, with an ambiguous
     outcome.
   - Use idempotency keys where effects must happen exactly once.
6. **Forwarded headers are permissive by default,** as on `next start`. Use
   `--trusted-proxy` or `--strip-forwarded-headers` in production.
7. **Pages Router tail latency.** The proxied open-loop p99 is a documented
   GC trade-off.
8. **Image transformation throughput at the default settings.**
   - `--image-concurrency` defaults to half the CPUs. At that setting,
     transformations run at about 0.67× of `sharp`'s rate on the measured
     workload.
   - Each transformation uses about 20 % less CPU than `sharp`'s.
   - With `--image-concurrency` equal to the CPU count, NextRS transforms
     about 1.3× as many images per second as `next start`, with a fifth of
     its memory.
   - Raise the setting on image-heavy deployments that have CPU to spare.
9. **Not available yet:**
   - a per-request access log or request ID;
   - response compression;
   - edge-runtime routes and middleware;
   - interception routes.

## Distribution

GitHub release archive only. NextRS is not on crates.io; the crate named
`nextrs` there is an unrelated project.

## Verifying the download

```bash
sha256sum -c nextrs-v0.1.0-rc.1-linux-x86_64.tar.gz.sha256
```

`BUILD-INFO.json` in the archive records the source commit, compiler
(rustc 1.98.0), Cargo profile (`dist`) and the binary's SHA-256.

Rebuilding the same commit does not produce a bit-identical binary. The
published binary is the one that went through the validation above.
